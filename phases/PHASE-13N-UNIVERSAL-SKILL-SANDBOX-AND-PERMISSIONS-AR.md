# PHASE13N — Universal Skill Sandbox & Permission Engine

**الحالة:** مصدر المرحلة وُصل إلى CI؛ لا تُعد المرحلة معتمدة نهائياً قبل نجاح اختبارات Flutter وAndroid في GitHub Actions وتجربة التشغيل على جهاز فعلي.

## الهدف

إنشاء حد صلاحيات عام لمحرك تشغيل المهارات، لا يعتمد على أسماء حزمة مهارات إنتاج الفيديو الست. ملفات المهارات الست مجرد أمثلة؛ محرك الأذونات والـexecutor ومكوّنات Android لا تحتوي قواعد مرتبطة بأسمائها.

تغطي هذه المرحلة **مشغّل السكريبتات المحلي الحالي**. وهي لا تدّعي أن MCP أو HTTP/API أو CLI مستقل أو Workflow أصبح قابلاً للتنفيذ تلقائياً لمجرد إمكان اكتشاف تعريفه. كل نوع يحتاج إلى adapter صريح يعلن قدراته، يربطها بسياسة الأذونات، ويملك اختبارات تشغيل خاصة به.

## التغييرات

### 1. مراجعة الأذونات ومنح التنفيذ

أضيف `SkillExecutionPermissionPolicy` كطبقة عامة للمشغّل المحلي الحالي:

- تضم قائمة الأذونات المطلوبة التي تعكس ما يستطيع PRoot الوصول إليه حالياً، بما في ذلك الكتابة إلى RootFS المشترك واتصال الشبكة وتثبيت الحزم.
- تمنع المعرّفات غير المعروفة، وتمنع الأذونات المعروفة التي لا يملك مشغّل السكريبت المحلي adapter أصلياً لها.
- تفصل المراجعة عن المنح؛ المراجعة وحدها لا تسمح بالتنفيذ.
- يشترط مسار `skill_execute` موافقة يدوية لكل تشغيل، حتى في Full Access.
- بعد عودة الموافقة، يصدر KELIVO منحة مرتبطة بكائن مراجعة محدد ومعرّف تشغيل واحد. يستهلكها Executor عند التحقق قبل تحليل أو تشغيل السكريبت، ويمنع إعادة استخدام كائن المنحة نفسه.
- لا يقبل معرّف المنحة من مدخلات النموذج؛ ينشئه التطبيق ويحفظه في سجل الموافقة.

### 2. فصل مساحات كل تشغيل

بدلاً من تركيب مجلد تشغيل واحد قابل للكتابة، أصبح Android Skill Executor يطلب أربع مساحات مستقلة:

| المساحة | المسار داخل PRoot | طلب الكتابة |
|---|---|---|
| مصدر المهارة المنسوخ والمتحقق من بصمته | `/run/kelivo-skill/source` | قراءة فقط |
| ملفات ومدخلات التشغيل | `/run/kelivo-skill/io/input` | قراءة فقط |
| مخرجات المهارة المتوقعة | `/run/kelivo-skill/io/output` | كتابة |
| الملفات المؤقتة | `/run/kelivo-skill/io/tmp` | كتابة |

لا يركّب Executor جذر المشروع أو سجل المحادثة أو شجرة المهارات المثبتة أو المجلدات الخارجية ضمن طلب Skill. وتبقى ملفات المصدر والمدخلات نسخاً مرحلية معزولة عن الملفات الحية.

### 3. حواجز أوامر القراءة فقط في Android

- ينشئ `WorkspacePlugin` ملف إعداد منفصلاً تحت `/run/kelivo/mount-readonly-prefixes-per-run/` لكل تشغيل متزامن، ويقدمه للبيئة عبر `KELIVO_READONLY_MOUNTS_FILE`؛ وبذلك لا يتعارض مع ملف الإعداد القديم الخاص بجلسات PTY.
- تُثبت wrappers لأوامر شائعة مثل `touch`, `tee`, `cp`, `mv`, `mkdir`, `rm`, `rmdir`, `ln`, `dd`.
- يضع Executor مسارات wrappers في بداية `PATH` مع الاحتفاظ بمسارات Profile الخاصة بـPython وNode.
- يحرر `ExecRunner` ملف الحاجز عند انتهاء العملية أو عند فشل تجهيز/بدء العملية، ويحذف wrappers التي يملكها KELIVO عندما ينتهي آخر تشغيل ولا يبقى إعداد PTY نشطاً.
- لا تستبدل هذه الحواجز أدوات المستخدم الأصلية التي لا يملكها KELIVO، ولا تمسح wrappers ما دامت هناك إعدادات تشغيل فعّالة.

## حدود الأمان التي يجب عدم إخفائها

**PRoot ليس عزلاً أمنياً على مستوى Kernel.** هذه المرحلة تفرض موافقات وحدوداً داخل التطبيق وتقلل التعرض العرضي، لكنها ليست بديلاً عن Android OS sandbox منفصل أو حاوية/VM ذات تحكم فعلي.

- RootFS النشط مشترك وقابل للكتابة من عملية الضيف؛ لذلك ما زال خطر تعديل النظام والحزم قائماً بعد الموافقة.
- اتصال الشبكة غير محظور من backend الحالي، ولا يوجد host allowlist مفروض من طبقة النظام.
- أعلام `readOnly` في BindMount لا تتحول إلى mount flags يفرضها Kernel في PRoot.
- wrappers تغطي أوامر شائعة فقط؛ يمكن تجاوزها عبر مفسرات Python/Node، أو إعادة توجيه shell، أو استدعاءات النظام المباشرة، أو المسار المطلق للأداة، أو تعديل ملفات الحاجز المشتركة.
- الأذونات الحساسة التي تحتاج إلى Android adapter مثل الموقع أو التقويم تُرفض لمشغّل السكريبتات الحالي بدلاً من اعتبارها ممنوحة.
- هذه المرحلة لا تمرر قيم أسرار Android أو متغيرات Runtime Profile المخصصة إلى عملية Skill. لا يعني ذلك أن الشبكة محظورة؛ فالعملية قد تتصل بالخدمات التي يسمح لها RootFS والوصول الشبكي الحالي بها.

لذلك لا تصنف الواجهة هذه البيئة بأنها `kernelSandbox=true` ولا تعرض الشبكة على أنها مقيّدة. يلزم backend أقوى مستقل عن PRoot قبل رفع مستوى ضمان العزل.

## التوافق مع المهارات العامة

السياسة لا تعتمد على `ig-profile` أو `ig-reel` أو `ig-viral` أو مهارات الفيديو الأخرى. يُضاف دعم نوع مهارة جديد عبر adapter يحدد:

1. نوع القدرة ونقاط الدخول ووسائطها.
2. الصلاحيات الفعلية التي يحتاجها هذا adapter.
3. الإنفاذ الحقيقي المتاح لكل صلاحية، وليس الوصف فقط.
4. موافقة المستخدم ونطاق المنحة ومدى صلاحيتها.
5. تقارير واختبارات إثبات تشغيل مستقلة.

حتى يكتمل adapter، تظل القدرة في حالة غير مدعومة أو Guidance-only ولا تُعامل على أنها جاهزة للتنفيذ.

## اختبارات المرحلة المضافة إلى CI

- اختبارات سياسة الأذونات، رفض الأذونات المجهولة/غير المدعومة، ومنع إعادة تشغيل المنحة.
- اختبارات حد التنفيذ وبيانات الموافقة دون حفظ قيم المدخلات والأسرار.
- اختبارات Skill Executor لمساحات المصدر والمدخلات والمخرجات وملفات tmp ومنع الإرسال بلا منحة.
- اختبار Android `MountWriteGuardsTest` لإعداد ملفات حواجز متزامنة لكل تشغيل وتنظيف wrappers.
- فحوص static preflight وCI wiring.

لا تعاد اختبارات PHASE13A–13D التاريخية. تُشغّل اختبارات Dart/Flutter وRobolectric وبناء APK من مسار GitHub Actions؛ لا تعتبر نجاحاً قبل ظهور سجلها الفعلي.

## معيار قبول المرحلة

لا تعتمد PHASE13N نهائياً إلا بعد نجاح syntax preflight، وCI self-test، واختبارات Flutter المركزة، واختبارات Android `MountWriteGuardsTest`، ثم نجاح Release ARM64 وتجربة تشغيل على Android تؤكد الموافقة لكل تشغيل، وفشل المنحة المفقودة أو المعاد استخدامها، وإمكان استرجاع مخرجات التشغيل من KELIVO.
