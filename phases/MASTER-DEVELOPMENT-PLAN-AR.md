# 1. القرار المنتجّي الذي يحكم كل التطوير

KELIVO ليس محرر فيديو تقليدياً، ولا تطبيقاً يحتوي قائمة ثابتة من أدوات الإنتاج. إنه **Conversation-First, Extensible Video Agent**.

المحادثة هي نقطة التحكم الوحيدة في الاستخدام المعتاد. لا يُطلب من المستخدم فتح شاشة منفصلة لتثبيت مهارة، أو اختيار مكتبة من قائمة ثابتة، أو إعداد مسار مونتاج يدوياً. يمكن أن تبقى صفحات العرض والإعداد والسجلات موجودة للمراجعة، لكن كل العمليات الأساسية يجب أن تكون قابلة للتنفيذ بأوامر المحادثة.

## 1.1 القاعدة الأساسية: لا محتوى إنتاج مفروض مسبقاً

لا تُضمّن المنصة افتراضياً أو كمتطلبات ثابتة:

- مهارة Remotion أو Manim أو Motion Canvas أو أي مهارة فيديو أخرى.
- محرك فيديو واحد مفروض على جميع المستخدمين.
- مكتبة مونتاج أو توليد صور أو صوت أو فيديو بعينها.
- مزود نماذج أو خدمة توليد واحدة.
- قوالب فيديو أو حزم مهارات إلزامية.
- قائمة ثابتة ونهائية من المكتبات التي يستطيع المستخدم تثبيتها.

كل هذه العناصر **Extensions اختيارية** يضيفها المستخدم أو يزيلها أو يحدّثها أو يستبدلها وقتما يريد.

## 1.2 ما الذي يبقى ثابتاً؟

لا يمكن جعل كل اعتماد في التطبيق نفسه قابلاً للتثبيت أثناء التشغيل. يظل داخل APK حد أدنى من البنية اللازمة لكي يعمل Kelivo:

- واجهة Flutter والمحادثة.
- مخزن المحادثات والإعدادات والمهام.
- محرك استدعاء الأدوات وإدارة السياق.
- موصل Android وKotlin وPRoot الحالي.
- مدير الإضافات والتبعيات العام.
- طبقة الأمان والصلاحيات وسجل العمليات.

هذه هي **النواة التقنية** وليست مكتبات إنتاج مفروضة. أما Remotion وManim وFFmpeg وNode/Python packages وغيرها من أدوات الإنتاج، فتُدار خارج حزم APK متى أمكن، داخل بيئة Android/Linux المعزولة، أو عبر API/MCP عند الحاجة.

أي مكتبة Android Native تتطلب تعديل Gradle أو Kotlin أو JNI أو إعادة بناء APK لا يمكن تثبيتها فعلياً في APK المثبت بمجرد أمر محادثة. لذلك لا نعرض هذا النوع على أنه تثبيت Runtime عادي؛ نوضح أنه يتطلب إصداراً جديداً من التطبيق. الأولوية لمحركات CLI القابلة للتثبيت داخل PRoot وللخدمات الخارجية ذات الواجهات القياسية.

# 2. أوضاع الإنتاج التي يجب دعمها

يختار المستخدم الوضع في المحادثة، ويمكنه تغييره لكل مهمة أو لكل مشروع.

## 2.1 Code-Based Video — الفيديو الذي يُنشأ بالكود

يكتب الوكيل ملفات المشروع البرمجية التي تصف المشاهد والإطارات والحركة والتوقيت والنصوص والمؤثرات والصوت. ثم يشغّل محرك التصيير لإنتاج الإطارات أو الفيديو النهائي.

لا يعني هذا أن Remotion هو المحرك الوحيد. قد يكون المحرك Remotion أو Manim أو Motion Canvas أو محركاً آخر يجلبه المستخدم من GitHub، أو سكربت Python/JavaScript/GLSL/FFmpeg مخصصاً. دور KELIVO هو تشغيل المحرك من خلال عقد عام، وليس فرض اسم أو مكتبة.

## 2.2 Model-Based Video — الفيديو الذي يولده نموذج

يستدعي الوكيل خدمة أو موصلاً يختاره المستخدم لتوليد مقاطع أو مشاهد من نص أو صورة. يتعامل مع الطلبات غير المتزامنة، وحالات الانتظار، وروابط النتائج، والتنزيل، وحدود التكلفة.

لا نفترض أن كل نموذج يدعم إخراج الفيديو. كل موصل يعلن قدراته الفعلية، مثل text-to-video وimage-to-video والمدة والأبعاد والصوت والقيود.

## 2.3 Hybrid Video — الإنتاج الهجين

يخلط الوكيل بين المشاهد المولدة من نموذج وبين مشاهد مكتوبة بالكود، ثم يستخدم الأدوات المتاحة لدمجها مع الصوت والترجمة والعناوين والرسوم والانتقالات.

مثال: توليد لقطات واقعية بواسطة API، وبناء العناوين والرسوم المتحركة بالكود، ثم دمج الجميع في ملف واحد.

## 2.4 Auto Select

يطلب المستخدم من الوكيل اختيار أفضل نهج. يقرأ الوكيل الهدف والمهارات والمحركات والموصلات المثبتة، ويقارن الإمكانات والتكلفة والوقت والقيود، ثم يختار أو يعرض سبب طلب تثبيت إضافة ناقصة.

يجب ألا يثبت الوكيل إضافة كبيرة أو مدفوعة أو ذات صلاحيات عالية دون أن يوضح ذلك للمستخدم وفق سياسة الموافقات التي يحددها.

# 3. فحص Kelivo الحالي: ما نستفيد منه وما يجب تغييره

الفحص هنا مبني على أرشيف Android-only الذي أُرسل في المحادثة، وليس على التخمين من README.

## 3.1 النواة الموجودة

| الجزء الحالي | المسار الأساسي | الاستفادة |
|---|---|---|
| محرك استدعاء الأدوات وجولات النموذج | `lib/core/services/api/generation/tool_loop_runner.dart` | نواة تنفيذ الأدوات وإرجاع النتائج للنموذج |
| كتالوج الأدوات | `lib/core/services/tools/built_in_tool_catalog.dart` | نقطة انطلاق لتسجيل الأدوات الأساسية والديناميكية |
| المحادثة وتجهيز الرسائل | `lib/features/home/services/message_generation_service.dart` و`message_builder_service.dart` | حقن سياق المهارات ومساحة العمل |
| إدارة المهارات | `lib/core/services/skills/` | استيراد وفحص وتخزين المهارات |
| نموذج المهارة | `lib/core/models/skill_record.dart` | حالة التثبيت والتفعيل والمصدر والاستخدام |
| ربط مهارات بالمحادثة | `lib/core/models/skills_binding.dart` | أساس نطاقات التفعيل |
| مساحة العمل | `lib/core/services/workspace/` | قراءة الملفات وكتابتها والبحث والتشغيل |
| أدوات مساحة العمل | `lib/core/services/workspace/workspace_tools_service.dart` | `shell`, `read_file`, `write_file`, `edit_file`, `list_dir`, `glob`, `grep`, `view_image` |
| Android PRoot | `lib/core/services/sandbox/` و`android/app/src/main/kotlin/.../workspace/` | بيئة تنفيذ Linux داخل Android |
| إدارة بعض متطلبات البيئة | `lib/core/services/sandbox/environment_dependencies.dart` | أساس لتطوير مدير تبعيات عام |
| MCP | `lib/core/services/mcp/` و`lib/features/mcp/` و`dependencies/mcp_client/` | اكتشاف وتشغيل أدوات خارجية |
| نماذج الذكاء الاصطناعي | `lib/core/models/model_spec.dart` و`lib/core/services/api/providers/` | أساس موصلات النماذج الحالية |
| الوسائط | `lib/core/services/asr/` و`tts/` و`lib/core/services/api/` | إمكانات إدخال/صوت يمكن توسيعها |

## 3.2 مهارات Kelivo الحالية

يوجد `SkillsService` ويتيح حالياً:

- الاستيراد من Markdown أو ZIP أو رابط GitHub.
- فحص `SKILL.md` وقراءة بياناته الوصفية.
- تخزين المهارات وإعادة فحص المجلد.
- التفعيل والتعطيل والحذف والتصدير.
- تحديد المهارات المسموح بها للمساعد أو المحادثة.
- حقن وصف المهارة في سياق النموذج، ثم إتاحة قراءة ملفاتها عبر أدوات مساحة العمل.

لكن توجد فجوتان واضحتان:

1. التثبيت والإدارة يمران أساساً عبر واجهة Skills وليس عبر أدوات محادثة رسمية مثل `install_skill` و`enable_skill` و`remove_skill`.
2. يوجد ربط مدمج لمهارتين داخل `SkillsService._bundledSkillFiles`: `skill-creator` و`visualize`، كما أن `visualize` له أولوية خاصة في `skills_prompt.dart`.

**قرار الخطة:** لا نضيف مهارات فيديو مدمجة جديدة. نراجع `skill-creator` و`visualize` ونفصل أي وظيفة أساسية يحتاجها التطبيق إلى Capability داخل النواة، ثم نوقف تثبيت المهارات المدمجة تلقائياً. في التثبيتات الجديدة يبدأ مخزن مهارات المستخدم فارغاً. في التحديثات القائمة لا نحذف محتوى المستخدم بصمت: نميز المهارة المدمجة غير المعدلة عن نسخة عدلها المستخدم؛ ننقل أي تعديلات شخصية إلى سجل مهارة مستخدم أو نطلب الاختيار قبل الإزالة. لا نحذف مهارات استوردها المستخدم.

## 3.3 حد السياق الحالي

`skills_prompt.dart` يحدد سقفاً ثابتاً قدره 20 مهارة مرئية ويحد وصف المهارة إلى عدد أحرف ثابت. هذا لا يلائم مكتبة كبيرة أو تركيب مهارات كثيرة.

**قرار الخطة:** ننتقل إلى progressive disclosure وفهرسة وصفية واسترجاع ذكي حسب المهمة، مع سقف سياق ديناميكي حسب ميزانية النموذج، وليس سقفاً ثابتاً يحد عدد المهارات التي يستطيع المستخدم تثبيتها.

## 3.4 مدير التبعيات الحالي

`environment_dependencies.dart` يحتوي enum ثابتاً لمتطلبات: Python وNode وGit وSSH والشبكة والأرشفة، ويعرّف حزم apt/apk وفحوصها مباشرة. توجد واجهة منفصلة لتثبيت هذه الفئات.

**الفجوة:** هذا مناسب للتبعيات الأساسية المعروفة، لكنه ليس مدير مكتبات عاماً يقبل اسم أداة أو حزمة من المحادثة ويكتشف مدير الحزم والإصدار والبيئة والنطاق تلقائياً.

**قرار الخطة:** نعيد بناء هذا الجزء حول Package Manager Adapters قابلة للتوسعة. لا نضيف FFmpeg أو Remotion أو Manim إلى enum ثابت؛ تصبح كل واحدة حزمة يطلبها المستخدم أو تتطلبها مهارة/إضافة.

## 3.5 مساحة العمل والتنفيذ الحالي

توجد أدوات Shell والملفات، وبيئة Android PRoot. لذلك لا نحتاج كتابة منفذ أوامر جديد من الصفر؛ نحتاج وضع سياسة موحدة للتبعيات والبيئات والعزل والسجلات، وتوصيلها بالوكيل.

يجب التفريق دائماً بين:

- تثبيت حزمة داخل Ubuntu/Debian/Alpine في PRoot.
- تثبيت حزمة داخل بيئة مشروع Python/Node.
- تنزيل ملف تنفيذي مستقل داخل مجلد أدوات.
- إضافة مكتبة Android Native تتطلب إعادة بناء APK.

كل واحدة لها طريقة تثبيت وفحص وإزالة مختلفة.

## 3.6 نماذج الوسائط

`ModelSpec` الحالي يعرّف video كوسيط إدخال، لكن مجموعة وسائط الإخراج المنظمة تستبعد video حالياً. لذلك يجب أن تكون قدرات توليد الفيديو في طبقة موصلات/مهام مستقلة أو توسيعاً مدروساً لنموذج القدرات، لا افتراضاً أن أي Model Provider موجود يمكنه توليد فيديو.

# 4. المعمارية المستهدفة: نواة ثابتة وإضافات متحركة

```text
KELIVO ANDROID APP
└── Conversation UI
    └── Agent Orchestrator
        ├── Intent & Task Planner
        ├── Capability Registry
        │   ├── Core Tools
        │   ├── Installed Skill Tools
        │   ├── MCP Tools
        │   ├── Engine Adapters
        │   └── Provider Connectors
        ├── Extension Manager
        │   ├── Skills
        │   ├── Engines
        │   ├── Tool Packs / MCP Connectors
        │   ├── Provider Connectors
        │   ├── Workflows
        │   └── Templates / Assets
        ├── Dependency & Runtime Manager
        │   ├── Package Manager Adapters
        │   ├── Runtime Detection
        │   ├── Environment Profiles
        │   └── Lock / Verify / Rollback
        ├── Project Workspace & Artifact Store
        ├── Video Job DAG / Checkpoints
        └── Quality Review & Recovery

ANDROID EXECUTION
├── PRoot Linux workspace
├── Project-specific environments
├── Downloaded CLI engines and scripts
├── API-based generation tasks
└── Android native bridges only when needed
```

## 4.1 Capability Registry

سجل مركزي يعلن ما هو متاح الآن للوكيل. كل قدرة تسجل:

- الاسم والمعرف الفريد.
- النوع: tool / skill / engine / provider / workflow.
- الإصدار والمصدر.
- وصف الاستخدام ومخطط المدخلات والمخرجات.
- البيئات والمعماريات المدعومة.
- التبعيات اللازمة.
- الصلاحيات المطلوبة.
- الحالة: مثبت، مفعل، غير متوافق، يحتاج تحديثاً، أو فشل التحقق.

لا نطلب من النموذج تخمين أسماء الأدوات. يقرأ الوكيل من السجل الأدوات المتاحة فعلاً، ويعيد بناء قائمة الأدوات بعد التثبيت أو التعطيل.

## 4.2 أنواع الإضافات التي يجب أن يستطيع المستخدم تثبيتها

1. **Skill:** تعليمات Agent Skills قياسية مع ملفات scripts/references/assets اختيارية.
2. **Engine Adapter:** تعريف طريقة إنشاء مشروع وتشغيله وتصويره وإلغاء التصيير وفحص الناتج لمحرك معين.
3. **Tool Pack / MCP Connector:** مجموعة أدوات محلية أو خادم MCP خارجي.
4. **Provider Connector:** موصل خدمة/واجهة API، بما في ذلك توليد الفيديو أو الصور أو الصوت.
5. **Workflow Pack:** تعريف سير عمل يجمع عدة مهارات ومحركات ومزودات، دون أن يكون محركاً ثابتاً.
6. **Template / Asset Pack:** قوالب ومكونات مرئية وأصوات وخطوط ومواد مرخصة.

كل نوع اختياري. ولا يشترط تثبيت حزمة من كل الأنواع كي يعمل التطبيق.

# 5. معيار المهارات والتوافق

## 5.1 Agent Skills هو المدخل القياسي

تدعم النواة مجلد المهارة القياسي:

```text
my-skill/
├── SKILL.md
├── scripts/       # optional
├── references/    # optional
├── assets/        # optional
└── ...
```

يُقرأ الاسم والوصف أولاً، ولا تُحمّل التعليمات الكاملة والملفات المرجعية إلا عندما يختار الوكيل المهارة. هذا progressive disclosure يمنع ضخ كل محتوى جميع المهارات في السياق.

## 5.2 لا نغيّر مواصفة SKILL.md

ملف `SKILL.md` يظل متوافقاً مع الصيغة المفتوحة. المواصفة الأساسية توثق الاسم والوصف والتعليمات والمراجع والملفات والسكربتات، لكنها لا تكفي وحدها لتعريف كل تفاصيل التبعيات والصلاحيات وآلية تثبيت مكتبات كل مهارة.

لذلك نضيف **بيان Kelivo اختياري** منفصلاً، مثلاً `kelivo.extension.yaml`، دون فرضه على المهارات القياسية:

```yaml
schemaVersion: 1
id: publisher.skill-id
kind: skill
version: 1.2.0
entrypoint: SKILL.md
requires:
  runtimes: []
  packages: []
  executables: []
capabilities: []
permissions:
  filesystem: [workspace]
  network: []
  shell: []
compatibility:
  os: [android-proot-linux]
  architectures: [aarch64]
healthChecks: []
```

هذا مثال تصميمي لعقد Kelivo، وليس جزءاً من Agent Skills standard. كل قائمة اختيارية؛ لا نفترض أن كل مهارة تحتاج تبعيات أو سكربتات.

## 5.3 مصادر التثبيت

يجب أن يقبل مدير الإضافات:

- GitHub owner/repo.
- رابط GitHub إلى مجلد فرعي أو Skill محددة.
- Branch أو Tag أو Commit محدد.
- ZIP محلي أو رابط تنزيل موثوق.
- مجلد محلي داخل مساحة العمل.
- فهرس مهارات/حزم متوافق، مع إمكانية إضافة مصادر أخرى لاحقاً.
- Skills Packs تحتوي أكثر من مهارة.
- مصادر خاصة عبر GitHub App/OAuth أو Token محفوظ في مخزن أسرار، دون إظهاره في السجلات.

الاستيراد من `skills.sh` أو عبر CLI متوافق يكون Adapter للمصدر/المنصة، وليس شرطاً لتشغيل المهارات. يجب ألا يعتمد تثبيت مهارة بسيطة على تثبيت Node.js أو CLI آخر إذا كان تنزيل ملفاتها والتحقق منها ممكناً مباشرة.

## 5.4 دورة حياة المهارة

كل عملية متاحة من المحادثة:

- `list_skills`: عرض المهارات ومصادرها وإصداراتها.
- `search_skills`: البحث في مصدر أو مستودع.
- `inspect_skill`: قراءة وصفها ومتطلباتها وصلاحياتها.
- `install_skill`: تنزيل وفحص وتسجيل المهارة.
- `enable_skill` / `disable_skill`.
- `update_skill` / `update_all_skills`.
- `remove_skill` مع الحفاظ على ملفات المشروع التي أنشأتها المهارة.
- `rollback_skill`: الرجوع لإصدار سابق إن كان محفوظاً.
- `export_skill` ومشاركة الحزمة.

لا تنجح عملية التثبيت بمجرد تنزيل مجلد. يجب أن تنتهي بـ validation، وتسجيل المصدر والإصدار والبصمة، وفحص SKILL.md، وتحديد صلاحياتها، ثم إظهار نتيجة مفهومة داخل المحادثة.

# 6. تركيب مهارات متعددة في المهمة الواحدة

هذه ميزة أساسية وليست خياراً ثانوياً.

## 6.1 أوضاع اختيار المهارات

- **Auto:** الوكيل يكتشف المهارات المناسبة من أوصافها ويقترح المجموعة.
- **Explicit:** المستخدم يطلب أسماء محددة ويُلزم الوكيل باستخدامها حيث تنطبق.
- **Project Default:** مجموعة افتراضية قابلة للتعديل لمشروع معين.
- **Conversation Override:** اختيار مؤقت لهذه المحادثة فقط.
- **Exclude:** منع مهارة معينة حتى لو رشحها الوكيل.
- **Pinned Version:** تثبيت إصدار محدد من المهارة حتى لا يتغير سلوك المشروع بعد تحديثها.

## 6.2 Skill Composition Planner

عندما يطلب المستخدم دمج عدة مهارات، يحول الوكيل المهمة إلى خطة مراحل/عُقد:

مثال:

```text
طلب المستخدم
   ↓
Skill A: Story & Script Planning
   ↓
Skill B: Code-based Scene Generation ───────┐
   ↓                                        │
Skill C: Voice & Sound Design               │
   ↓                                        │
Skill D: Captions & Timing                  │
   ↓                                        │
Skill E: Render & Export  ←─────────────────┘
   ↓
Skill F: Visual Quality Review
   ↓
Final Video + Editable Project
```

هذه الأسماء أمثلة توضيحية فقط وليست مهارات مدمجة أو مفروضة.

## 6.3 حل التعارضات

على المخطط اكتشاف:

- مهارتين تحاولان استخدام محركين مختلفين في الخطوة نفسها.
- نسختين غير متوافقتين من مكتبة واحدة.
- مهارة تتطلب إصدار Node أو Python لا يوافق البيئة.
- مهارة تكتب في المسار نفسه الذي تستخدمه مهارة أخرى.
- تعريفات أدوات تتعارض أسماؤها.
- متطلبات صلاحيات متعارضة أو غير مسموحة.

إذا كان التعارض قابلاً للحل، يقترح ترتيباً أو بيئة منفصلة. وإذا كان يؤثر في الناتج، يشرح الاختيارات للمستخدم بدلاً من اتخاذ قرار مبهم.

## 6.4 مشاركة النتائج بين المهارات

يجب أن تتبادل المهارات ملفات ومخرجات منظمة، لا مجرد نصوص طويلة في المحادثة. نستخدم Artifact Contracts مثل:

- `script.json`
- `storyboard.json`
- `scene-brief.json`
- `voice.wav`
- `captions.srt`
- `render.mp4`
- `render-report.json`

كل مهارة تعلن المخرجات التي تقرؤها/تنشئها. لا نفرض هذه الأسماء على كل محرك؛ إنها عقود داخلية يمكن للموصلات تكييفها.

## 6.5 إدارة السياق

- تحميل وصف جميع المهارات المثبتة فقط.
- تحميل `SKILL.md` للمهارات المختارة للمهمة.
- قراءة references عند الحاجة.
- عدم نسخ مجلدات المهارات كلها داخل System Prompt.
- ميزانية سياق متغيرة حسب النموذج وحجم المهمة.
- سجل يوضح المهارات التي استُخدمت وسبب اختيار كل واحدة.

# 7. مدير التبعيات والمكتبات العام

## 7.1 مبدأ التصميم

المستخدم يكتب اسم الأداة أو المكتبة كما يعرفها، مثلاً:

> ثبّت FFmpeg في بيئة الإنتاج الحالية، ثم تحقق من ffmpeg وffprobe.

الوكيل لا يملك قائمة مغلقة بأسماء المكتبات. يحدد مدير التبعيات:

1. ما الحزمة المقصودة؟
2. ما البيئة النشطة؟
3. ما مدير الحزم الذي يديرها؟
4. هل الحزمة مثبتة؟ وبأي إصدار؟
5. هل توجد متطلبات أصلية؟
6. هل ستثبت عالمياً داخل PRoot أم داخل المشروع؟
7. كيف يختبر نجاح التثبيت؟
8. كيف يتراجع عن العملية عند الفشل؟

## 7.2 Package Manager Adapters

تبدأ النواة بمحولات عامة قابلة للتوسعة لمديري الحزم التي تدعمها بيئة PRoot/المشاريع، مثل:

- apt/dpkg داخل Debian/Ubuntu.
- apk داخل Alpine.
- pip/venv أو uv داخل Python.
- npm/pnpm/yarn/bun داخل Node.js.
- cargo داخل Rust عند الحاجة.
- أدوات تنزيل الإصدارات الثنائية الموثقة من المصادر الرسمية.

هذه **محولات بروتوكول/مدير حزم** وليست قائمة بالمكتبات المثبتة. لا نثبت كل Runtime مسبقاً. يُثبت Runtime المطلوب عند أول طلب أو عند حاجة مهارة له.

لا نضيف مدير حزم إلا إذا كان متوافقاً مع Android ARM64 وبيئة التشغيل الحالية ويمكن التحقق من تثبيته وإزالته.

## 7.3 اكتشاف طريقة التثبيت

يستفيد المدير من:

- `SKILL.md` والتعليمات.
- `kelivo.extension.yaml` إن وجد.
- `package.json` وlock files.
- `pyproject.toml` و`requirements.txt`.
- ملفات إعداد أخرى يتعرف عليها Adapter.
- تعليمات المحرك الرسمية.
- أوامر preflight التي يوفرها Extension Adapter.

لا ينفذ أوامر تثبيت مستنتجة من نص عشوائي قبل التحقق من مصدرها ومعناها.

## 7.4 نطاقات التثبيت

| النطاق | المعنى | الاستخدام |
|---|---|---|
| Runtime Base | أدوات مشتركة في PRoot | الأدوات التي يريد المستخدم توفرها دائماً |
| Project Environment | متطلبات مشروع بعينه | منع تلويث مشاريع أخرى |
| Extension Environment | تبعيات حزمة محددة | تثبيت Skill/Engine مع عزلها قدر الإمكان |
| Task Environment | بيئة مؤقتة للمهمة | تجارب أو إصدارات متعارضة |

يختار الوكيل أقل نطاق يحقق الهدف، ويخبر المستخدم بمكان التثبيت.

## 7.5 خصائص مدير التبعيات

- install/check/upgrade/remove/pin/unpin.
- اكتشاف الإصدارات ومطابقة قيود المهارات.
- الاحتفاظ بسجل الحزم ومصدرها وأمر تثبيتها.
- حفظ lockfile لكل مشروع/بيئة.
- فحوص بعد التثبيت: وجود الأمر، الإصدار، smoke test.
- كشف تعارضات الإصدارات.
- تخزين مؤقت للحزم لتقليل إعادة التنزيل.
- استئناف التنزيلات القابلة للاستئناف.
- تقرير المساحة المستخدمة.
- rollback قدر الإمكان، أو توضيح الحزم التي لا يدعم مديرها الإزالة الآمنة.

## 7.6 التثبيت التلقائي وإعادة المحاولة

إذا فشل سكربت إنتاج بسبب `ffmpeg: command not found`:

1. يحلل الوكيل الخطأ.
2. يتحقق أن الأمر مفقود بالفعل.
3. يحدد البيئة/المشروع الذي نفذ داخله الأمر.
4. يبحث عن مصدر الحزمة المناسب ويحل التبعيات.
5. ينفذ التثبيت وفق سياسة موافقات المستخدم.
6. يتحقق من `ffmpeg -version` و`ffprobe -version` أو health check مناسب.
7. يستأنف من آخر checkpoint صالح، لا من أول المهمة.
8. يحد عدد محاولات الإصلاح ويعرض سبب التوقف إن لم ينجح.

يجب عدم إعادة تشغيل المهمة بالكامل إن كانت قد أنتجت مشاهد أو ملفات صالحة بالفعل.

# 8. محركات الفيديو: لا محرك ثابت ولا قائمة مغلقة

## 8.1 Engine Adapter Contract

أي محرك يرغب المستخدم في تثبيته يجب أن يستطيع الإعلان عن واجهة تشغيل موحدة، إما من خلال Adapter قابل للتثبيت أو عبر مهارات/سكربتات عامة:

- `inspect`: فحص التوافق والإصدار والقدرات.
- `requirements`: إعلان التبعيات.
- `install`: إعداد بيئة المحرك عند الحاجة.
- `create_project`: إنشاء مشروع أو هيكل ملفات.
- `render`: تنفيذ عملية التصيير.
- `preview`: إنشاء صورة/عينة/معاينة إن كان مدعوماً.
- `cancel`: إيقاف عملية التصيير.
- `inspect_output`: فحص الناتج.
- `export_artifacts`: تسليم MP4 والملفات المصدرية والتقارير.

لا يلزم أن يدعم كل محرك جميع الوظائف. تسجل القدرات المدعومة فعلياً فقط.

## 8.2 تثبيت محرك جديد

أمثلة أوامر مستقبلية:

- «ابحث عن محرك مناسب لإنشاء فيديو بالكود وثبته».
- «ثبّت محرك Remotion من مصدره الرسمي».
- «أزل محرك Manim من بيئة هذا المشروع فقط».
- «اجعل المحرك X افتراضياً لهذا المشروع، لكن لا تغيّر المشاريع الأخرى».
- «قارن المحركات المثبتة لهذه المهمة».

الأسماء أعلاه أمثلة لأوامر، وليست قائمة محركات مدمجة.

## 8.3 تقييم التوافق على Android ARM64

لا يكفي أن يعلن المشروع أنه يدعم Linux. يجب اختباره داخل PRoot على Android:

- المعمارية ARM64.
- نسخة glibc/Alpine/Debian المطلوبة.
- توفر Chromium/Browser إن احتاجه المحرك.
- دعم headless rendering.
- استهلاك RAM والمساحة.
- معالجة GPU أو fallback إلى CPU.
- إتاحة إلغاء العملية.
- اكتمال التصدير والملف صالح للقراءة.

لا نعتمد محركاً بشكل افتراضي حتى ينجح اختبار حقيقي على هاتف Android. قد تكون بعض المحركات مناسبة لخادم بعيد أو جهاز آخر ولا تكون مناسبة للتصيير المحلي على الهاتف. يوضح KELIVO موقع التنفيذ قبل بدء المهمة.

**مثال يوضح ضرورة هذا الفحص:** وثائق Remotion الحالية تشترط Linux مع glibc 2.35 أو أحدث، وتذكر أن Alpine غير مدعوم؛ لذلك لا يكفي أن يكون المحرك Node.js قابلاً للتثبيت، بل يجب التحقق من Rootfs الفعلي داخل PRoot. وبالنسبة إلى Manim، توصي وثائقه ببيئة Python معزولة مثل virtual environment لتجنب تلويث Python النظام. هذان مثالان على ضرورة أن تكون متطلبات كل محرك ديناميكية ومحددة من وثائقه/حزمته، لا مكتوبة في قائمة واحدة لجميع المحركات.

# 13. الأمان والثقة والصلاحيات

المهارة قد تكون Markdown فقط، وقد تحتوي أيضاً سكربتات تنفذ أوامر. لذلك لا نعامل كل Skill على أنها تعليمات بريئة.

## 13.1 فحص ما قبل التثبيت

- التحقق من مسار المصدر والفرع/Commit.
- فحص ZIP traversal والروابط الرمزية والمسارات الخارجة من جذر الحزمة.
- حدود للحجم وعدد الملفات.
- تحليل SKILL.md والبيان الاختياري.
- عرض السكربتات وأوامر التثبيت والصلاحيات.
- فحص الأسرار الظاهرة والمفاتيح المضمنة.
- تسجيل المصدر والبصمة والإصدار.
- عدم تنفيذ lifecycle scripts تلقائياً لمجرد تنزيل الحزمة.

## 13.2 مستويات الثقة

1. **Review Mode:** تنزيل وفحص وعرض المطلوب، ولا يشغّل السكربتات حتى موافقة المستخدم.
2. **Install-on-Request:** أمر المستخدم الصريح يسمح بالتثبيت ضمن نطاق محدد، مع تأكيد إضافي للأوامر الحساسة.
3. **Trusted Source Auto Mode:** يثق المستخدم بمصدر/ناشر محدد، ويمكن تنفيذ عمليات التثبيت والاختبار ضمن صلاحيات محصورة.
4. **Restricted Auto Mode:** يسمح بالتنفيذ التلقائي داخل مساحة مشروع معزولة، دون وصول إلى ملفات المستخدم الخاصة أو الأسرار أو صلاحيات Android الواسعة.

يجب أن يكون خيار الثقة قابلاً للتعديل والإلغاء في أي وقت.

## 13.3 الموافقات

لا نطلب موافقة يدوية على كل خطوة عادية إذا اختار المستخدم وضعاً تلقائياً، لكن نوقف العملية أو نطلب موافقة عند:

- تثبيت مصدر غير معروف يشغّل سكربتات.
- الوصول إلى مفاتيح أو أسرار.
- إرسال ملفات إلى خدمة خارجية.
- إنفاق رصيد API مدفوع فوق حد المستخدم.
- الكتابة خارج مجلد المشروع المسموح.
- تغيير Rootfs أو حذف بيانات بيئة كاملة.
- إزالة مكتبات يعتمد عليها مشروع آخر.

MCP tools نفسها يجب أن تبقى مرئية للمستخدم مع إمكانية رفض التنفيذ؛ هذا يتوافق مع توجيهات السلامة في مواصفة MCP.

# 15. مراحل التنفيذ التفصيلية

## PHASE 0 — Baseline & Source Contract

**الهدف:** تثبيت نسخة Kelivo الحالية التي نجح APK الخاص بها، ومنع كسر وظائفها خلال إعادة التصميم.

**المهام:**
1. تثبيت commit مرجعي ونسخة APK ناجحة وSHA-256.
2. تسجيل نسخة Flutter/Gradle/Java/NDK وWorkflow.
3. تشغيل الاختبارات الحالية الممكنة وتسجيل الاختبارات غير القابلة للتنفيذ.
4. توثيق خدمات Skills وWorkspace وPRoot وMCP وModel APIs وقاعدة البيانات.
5. توثيق مجلدات التخزين وسلوك النسخ الاحتياطي.
6. تتبع كل استخدام لمهارتي `skill-creator` و`visualize` قبل نقل وظائفهما.
7. إعداد اختبارات Regression للمحادثة واستدعاء الأدوات وPRoot والتثبيت الحالي.

**معايير القبول:** APK الأساسي يبنى، تفتح المحادثة، ينجح استدعاء أداة بسيطة، وتعمل مساحة PRoot دون تغيير.

## PHASE 1 — Modular Core & Extension Registry

**الهدف:** إنشاء سجل موحد لجميع الإمكانات المثبتة من دون إضافة مهارات أو محركات فيديو افتراضية.

**المهام:**
1. تعريف Extension ID وKind وVersion وSource وDigest وCompatibility وPermissions.
2. إنشاء مخزن Registry وRepository API.
3. إضافة حالات lifecycle: discovered, downloaded, validated, installed, enabled, disabled, incompatible, update_available, failed.
4. فصل أنواع Skill/Engine/Tool/Provider/Workflow/Asset.
5. إضافة سجل نسخ ومصدر لكل إضافة.
6. فصل Core Capabilities عن Extensions القابلة للإزالة.
7. نقل وظائف النظام اللازمة من المهارات المدمجة إلى النواة، وإيقاف seeding الافتراضي للمهارات.
8. لا نضيف تعقيداً لترحيل أو حفظ بيانات الاختبار بين نسخ التطوير؛ المستخدم يمسح بيانات التطبيق عند إعادة التثبيت. نحافظ على صحة قاعدة البيانات الحالية فقط، ولا نُدخل مسارات ترحيل غير لازمة.

**معايير القبول:** التثبيت الجديد يبدأ دون مهارات فيديو أو محركات أو مكتبات إنتاج مثبتة؛ وتظل المحادثة وPRoot والأدوات الأساسية تعمل.

## PHASE 2 — Conversational Extension Commands

**الهدف:** إدارة دورة حياة المهارات من المحادثة عبر أدوات Typed مرتبطة بخدمات Skills وExtension Registry الفعلية، مع إظهار التقدم والنتائج في بطاقة أداة المحادثة.

**أدوات المحادثة المنفذة:**
- `extension_search`
- `extension_inspect`
- `extension_install`
- `extension_update`
- `extension_enable`
- `extension_disable`
- `extension_remove`
- `extension_rollback`
- `extension_list`

**نطاق التنفيذ في هذه المرحلة:**
1. البحث في المهارات المثبتة والبحث العام في مستودعات GitHub العامة. نتائج GitHub هي مرشحات أولية فقط وليست دليلاً على صحة Skill.
2. فحص Skill مثبتة أو معاينة مصدر GitHub/ملف/مجلد محلي دون تشغيل أي سكربت.
3. تثبيت Skill واحدة من رابط GitHub عام يحدد مجلداً واحداً أو من ملف Markdown أو ZIP أو مجلد داخل Workspace مسموح.
4. في تنفيذ Phase 2 الأول، كان المستودع متعدد المهارات يتطلب تحديد مجلد فرعي واحد. Phase 3 يضيف الآن اكتشاف عدة Skills داخل المستودع واختيار واحدة أو أكثر منها.
5. تفعيل Skill أو تعطيلها أو تحديثها من مصدر GitHub العام المسجل أو مصدر بديل صريح.
6. حفظ Snapshot قبل التحديث ودعم Rollback إلى الإصدار السابق.
7. إزالة Skill وملفاتها ولقطات التراجع.
8. تحديث Extension Registry ومصدر Skill فور نجاح التثبيت أو التحديث أو الإزالة.
9. إظهار حالة العملية وتقدم التنزيل/الاستيراد ضمن أداة المحادثة، مع ربط إلغاء المحادثة بإلغاء التنزيل/النسخ حيث يدعم المسار ذلك.
10. تسجيل سجل محدود الحجم للعمليات مع حالاتها ومرحلتها ورمز خطأ غير حساس.
11. رفض مسارات الملفات خارج Workspace mounts، ورفض روابط GitHub التي تحمل userinfo أو مفاتيح/رموز في query أو مضيفات غير معتمدة.
12. تنزيل ملفات المهارة والتحقق من هيكلها وبياناتها الوصفية فقط؛ لا يتم تشغيل `scripts/` تلقائياً أثناء التثبيت.

**القيود التي كانت سارية عند تنفيذ Phase 2 (تم توسيع دعم المهارات منها في Phase 3):**
- نوع الإضافة الذي يملك Installer فعلياً هو `skill` فقط. أنواع engine/tool/provider/workflow/asset تبقى في Extension Registry دون الادعاء بأنها قابلة للتثبيت بعد.
- في نطاق Phase 2 كان GitHub العام فقط؛ أضيفت المصادقة المحمية والاستيراد المتعدد في Phase 3.

5. إضافة `video_engine.resource_preflight`، وفرض Resource Guard قبل أمر Render المحلي؛ التحذير للضغط المتوسط والحظر للضغط الحرج المقاس فقط.

7. إضافة فحص Release ثابت يشمل ARM64، وإيقاف Android backup، واستبعاد مفاتيح التوقيع، ومراجعة secure storage، وصلاحيات GitHub Actions.
8. توثيق استثناء `usesCleartextTraffic=true` الحالي: توجد مرايا HTTP لـ PRoot وعمليات localhost وبعض موارد HTTP المستوردة/التي يقدمها المستخدم. هذا استثناء واسع ومخاطرة متبقية يجب تضييقها في ترحيل شبكي مختبر أو قبولها صراحة قبل النشر العام.

**ترتيب التنفيذ:** أُجيز إعداد checkpoints المصدر لـ13B و13C ثم 13D بناءً على طلب المستخدم المباشر مع بقاء بوابات 13A–13C مفتوحة. هذا لا يعني قبولًا بأثر رجعي أو إغلاق متطلبات MCP في 13B. لا تنتقل إلى أي مرحلة لاحقة قبل تشغيل CI وبناء Android ARM64 وتجارب الهاتف وإغلاق مراجعة عزل RootFS والأسرار. لا تعتبر PRoot حدًا أمنيًا على مستوى النواة.

# الخلاصة التنفيذية

KELIVO يجب أن يكون **نواة محادثة ووكلاء وإدارة إضافات**، أما مهارات الإنتاج ومحركات الفيديو والمكتبات ومزودات النماذج فهي اختيارات المستخدم.

لا نضع في التطبيق قائمة جامدة بمهارات أو مكتبات فيديو. نجهز آلية عامة لاكتشافها وتثبيتها والتحقق منها وربطها ودمجها وإزالتها، ثم نسمح للوكيل باستخدام أي تركيبة متوافقة يطلبها المستخدم.

المستخدم هو من يختار:

- أي Skills يثبت.
- أي مكتبات وأدوات يثبت.
- أي Engine يستخدم.
- أي مزود نموذج يختار.
- هل ينشئ الفيديو بالكود أو بالنماذج أو بالطريقة الهجينة.
- هل يستخدم مهارة واحدة أو عدة مهارات معاً.
- هل يجعل الاختيار لمهمة واحدة أو مشروع كامل.

**المبدأ النهائي: نبني النظام الذي يسمح بإضافة أي أداة مناسبة، ولا نبني التطبيق حول أداة واحدة.**


**آخر تحديث CI بعد التشغيل `42921174431` (2026-11-11):** اجتازت 13A عدد 60 اختبارًا، ثم فشلت حالة واحدة في 13B لأن `_validateArtifactContracts()` كان يحجب خطأ توافق Runtime Profile/interpreter. نُقلت فحوص عقد المخرجات إلى ما بعد فحص المفسّر دون حذف أي تحقق. ولتقليل الوقت قبل الحصول على APK، يشغّل المسار الافتراضي الآن 12 حالة smoke أساسية عبر خمسة أوامر Flutter فقط؛ كانت النسخة السابقة تشغّل 87 حالة قبل البناء وتستهلك 144 ثانية في preflight. اختبارات الانحدار الكاملة وتحليل Dart الشامل واختبار Native Asset المضيف المنفصل لم تُحذف، بل أصبحت اختيارية عبر `workflow_dispatch` ومدخل `run_extended_phase13_tests=true`. أما حزم GTK/GLib المضيفة فهي متطلب إعداد إلزامي قبل أي `flutter test` في الوضعين، كما أثبت التشغيل `42929627194`؛ ولا تدخل هذه الحزم في APK. لم تتوفر Flutter/Dart محليًا ولم يُبنَ APK في ذلك التعديل؛ القبول معلق على تشغيل CI. راجع `../build-report/PHASE-13B-CI-SMOKE-REDUCTION-AND-EXECUTOR-VALIDATION-FIX.md`.


**تصحيح CI بعد التشغيل `42929627194` (2026-11-11):** نجحت التهيئة والـpreflight، لكن أول `flutter test` في 13A أطلق Native Asset hook الخاص بـ`super_native_extensions 0.10.0-dev.2` لمنصة Linux المضيفة رغم أن حالات smoke لا تستورد الحافظة مباشرة. فشل Rust/Cargo لغياب `gobject-2.0.pc` و`glib-2.0.pc`. لذلك يُعاد تجهيز GTK/GLib على عامل Ubuntu في الوضع السريع والموسع قبل الاختبارات، وتتحقق بوابة preflight من الوحدات الأربع قبل إنشاء علامة نجاح التشغيل. لا يتغير عدد اختبارات smoke (12 حالة/5 استدعاءات Flutter)، وتبقى مجموعات الانحدار وتحليل Dart الشامل والـNative Asset smoke المنفصل اختيارية.

## Phase 13H — ZIP attachment routing and archive safety

- تصنيف ملفات ZIP والأرشيفات كملفات ثنائية قابلة للفحص، لا كنصوص أو مجلدات.
- استعادة MIME من امتداد الأرشيف عندما يعيد منتقي Android النوع العام `application/octet-stream`.
- منع مستخرج النصوص من تمرير محتويات الأرشيف إلى النموذج، مع الحفاظ على محلل DOCX المخصص.
- إعادة manifest للأرشيف إذا أخطأ النموذج واستدعى `list_dir` على `.zip`، وإظهار خطأ مزامنة واضح إذا لم يكن الملف موجوداً.
- الحفاظ على استيراد المهارات عبر `extension_install`، وفحص أعضاء ZIP عبر `read_file` و`archive_entry`.
- القبول النهائي مشروط باختبارات Phase 13H المركزة، وبناء ARM64، واختبار رفع واستيراد Skill ZIP على الهاتف. لا تعاد اختبارات 13A–13D.

راجع `PHASE-13H-ZIP-ATTACHMENT-ROUTING-AND-ARCHIVE-SAFETY-AR.md`.


## Phase 13I — موثوقية تشغيل المهام بعد مغادرة التطبيق

### المشكلة التي عالجتها المرحلة
كانت إعدادات الإصدارات السابقة تحتفظ أحياناً بـ `androidEnabled=false` عند وجود تخصيصات أخرى، وبذلك لا تبدأ خدمة Android الأمامية أصلاً. كما أن `GenerationForegroundService` كانت تستخدم `START_NOT_STICKY`، ويؤدي تدمير كائن الخدمة بصورة غير متوقعة إلى إرسال `interrupted` وإلغاء عمل Dart حتى لو كان محرك Flutter في العملية نفسها ما زال حياً.

### التنفيذ
- إضافة ترحيل إعدادات لمرة واحدة يفعّل `androidEnabled` وإشعارات الاكتمال للمستخدمين الحاليين، مع الاحتفاظ بإعدادات الخصوصية وOverlay وبقية التخصيصات. يمكن للمستخدم إيقاف التنفيذ لاحقاً من إعداداته.

### حدود Android الصريحة

## Phase 13J — اكتشاف متطلبات بيئة المهارات قبل التنفيذ

### المبدأ
بعد تثبيت أي Skill، يجب أولاً معرفة كل ما تحتاجه بيئة KELIVO لتشغيل قدراتها، حتى لو كان بعض ما تحتاجه غير متاح أو يتطلب تطويراً في KELIVO. التثبيت لا يساوي الجاهزية. المعلومات والتوافق تأتي أولاً؛ التثبيت والتنفيذ والاتصال الخارجي إجراءات لاحقة منفصلة تتطلب طلباً وموافقة.

### نطاق التنفيذ
- فهرسة runtimes/toolchains، أوامر CLI، حزم الاعتماديات، أوامر التثبيت المكتشفة نصياً، أسماء env/API variables، أسماء مضيفي الخدمات، وتعريفات MCP/HTTP API/Workflow/Native.
- فحص الملفات المساعدة وسكريبتات المهارة وملفات الإعداد والـdependency manifests بحدود آمنة مع تسجيل الملفات التي تجاوزت حدود التحليل.
- اختبار وجود أوامر allowlisted باستخدام `command -v` فقط في PRoot الأساسي، والتحقق من أسماء متغيرات KELIVO دون استخراج أو حفظ أو إرجاع قيم الأسرار. لا يُفحص اتصال الخدمات الخارجية.
- توضيح الفرق بين الأمر المثبّت في PRoot وبين ما يجب أن يوجد في Skill-owned Runtime Profile، وإظهار الحزم والموائمات غير المدعومة كمتطلبات معلقة لا كقدرات جاهزة.
- إظهار تقرير عربي بعد تثبيت Skill في واجهة المكتبة وفي استجابة `extension_install`؛ وإعادة فحصه عبر `extension_inspect`.
- تمرير `selectedSkillRequirements` إلى Skill Composition وإلزام المساعد بقراءة المتطلبات قبل ادعاء تنفيذ أي قدرة. يستطيع المستخدم سؤال المهارة مباشرة بعد التثبيت للاستفادة من تعليماتها النصية حتى إن لم تكن أدواتها التنفيذية جاهزة.
- تحديث فهرس المتطلبات للمهارات القديمة فقط عند فقدانه أو عدم تطابق بصمة المصدر، دون إعادة تثبيت المهارة أو تشغيل ملفاتها.

### قواعد السلامة والحدود
لا تثبيت تلقائي للحزم، ولا تنفيذ scripts، ولا بدء MCP server، ولا اتصالات API خلال discovery/import/inspect/composition. لا تُقرأ أو تُعرض قيم مفاتيح API؛ يكتشف النظام الأسماء فقط. عدم اكتشاف متطلب ليس دليلاً على عدم وجوده، وحدود الملفات غير المفحوصة تظهر في التقرير. لا تُضاف أدوات جديدة أو تغيّر مهارة أصلية إلى عضو حصري في Skill Pack.

### القبول
- تقرير مفصل يظهر بعد تثبيت مهارة جديدة، ويعرض الموجود/المفقود/غير المفحوص/غير المدعوم بدليل واضح.
- `extension_inspect` يعيد فحصاً حديثاً، بما في ذلك للمهارات القديمة.
- استدعاء المهارة فور التثبيت يتيح التعليمات النصية، بينما تمنع سياسة المساعد ادعاء تشغيل متطلب ناقص أو موائم غير موجود.
- اختبارات المتطلبات والمانيفست واستعادة المهارات القديمة وComposition والـprompt تنجح في GitHub Actions، ثم بناء ARM64 وتجربة على Android. لا تعاد اختبارات 13A–13D.

## Phase 13K — محرك جاهزية المهارات وسجل قدرات KELIVO

### المبدأ
لا يكفي تثبيت Skill أو تحليل ملفاتها لاعتبارها قابلة للتنفيذ. يجب أن يميز KELIVO بين اكتمال الاستيراد، وتحليل المتطلبات، والتحقق من الاعتماديات داخل ملف تشغيل المهارة، والإعداد، والاختبار الذاتي، والجاهزية النهائية. كما يجب أن يكون هناك سجل مستقل لقدرات التطبيق نفسه، لا ينشأ أو يتغير لمجرد تثبيت Skill أو Skill Pack.

### التنفيذ
- إضافة `SkillReadinessEngine` بحالات صريحة: blocked_incomplete_import، analysis_required، requirements_missing، unsupported_environment، dependencies_pending، configuration_required، validation_required، ready_for_instructions، ready.
- تقسيم الجاهزية إلى مراحل: Installed، Analyzed، Dependencies Resolved، Configured، Validated. لا تُمنح `ready` إلا بعد تحقق الاعتماديات في Skill Runtime Profile، والإعدادات والخدمات المطلوبة، وسجل اختبار ناجح بأدلة ووقت تحقق.
- اعتبار `ready_for_instructions` سماحاً باستخدام التوجيهات النصية فقط، دون الإيحاء بأن السكريبتات أو APIs أو MCP قابلة للتشغيل. أي قدرة مجهولة أو سكريبت مجهول الامتداد تُحجب بدلاً من تخمين Python أو افتراض دعمها.
- إضافة Capability Registry مستقل معرفه `kelivo.skill-capabilities` ويصف قدرات Agent Skill instructions وPython/Shell/Node local scripts وCLI وMCP وHTTP/API وWorkflow والأدوات الأصلية في التطبيق.
- تصنيف القدرات إلى مدمجة، مدمجة بشروط، معتمدة على البيئة، تحتاج موائماً يدوياً، أو تتطلب تطويراً في KELIVO. أي قدرة مجهولة تُحجب ولا تُعامل كمدعومة.
- عرض لوحة الجاهزية في صفحة تفاصيل Skill، مع فحص يدوي وتقرير كامل وزر لعرض سجل قدرات KELIVO العام.
- حفظ تقييم البيئة في import sidecar مربوط ببصمة المصدر التي فُحصت، ورفض حفظ نتيجة ذات بصمة قديمة. تعديل `SKILL.md` من داخل التطبيق يبطل فهرس المتطلبات والتقييم وبصمة المصدر لإعادة التحليل قبل أي ادعاء بالجاهزية.
- تمرير `selectedSkillRequirements` و`selectedSkillReadiness` وسجل قدرات التطبيق إلى Skill Composition، مع إلزام المساعد بطلب فحص حديث قبل الاتكال على القدرات التنفيذية.
- لا تثبيت تلقائي للحزم أو تنفيذ سكريبتات أو تشغيل MCP أو اتصالات API في هذه المرحلة. لا تغيير لملفات المهارات الأصلية أو ملكية Skill Packs.

### الاختبارات والقبول
