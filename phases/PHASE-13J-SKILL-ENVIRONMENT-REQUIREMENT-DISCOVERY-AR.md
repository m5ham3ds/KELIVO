# Phase 13J — اكتشاف متطلبات بيئة المهارات قبل التنفيذ

## الهدف

بعد تثبيت أي Agent Skill، لا يكفي أن يظهر كـ `installed` داخل مكتبة المهارات. يجب أن يعرف المستخدم والمساعد ما تحتاجه المهارة فعلياً من بيئات تشغيل وأدوات CLI وحزم ومفاتيح إعداد وخدمات خارجية وموائمات، وما المتاح أو المفقود أو غير المدعوم في KELIVO. هذه المرحلة تجعل **المعلومات أولاً**؛ لا تثبّت شيئاً ولا تشغّل سكريبتاً أثناء الفحص.

## التنفيذ

### 1. فهرس متطلبات ثابت مع سجل الاستيراد

أضيف `SkillRequirementsAnalyzer` في `lib/core/services/skills/skill_requirements.dart` ويربطه `SkillImportAnalyzer` بسجل الاستيراد. يحلل:

- بيئات التشغيل ومفسرات السكريبتات (Python، Node.js، Bash، Java، Ruby، PHP، Perl، Lua، R، PowerShell، Rust، Go وغيرها مما يمكن التعرف عليه).
- أوامر CLI من قائمة آمنة محددة ومن أقسام المتطلبات وملفات السكريبت/الإعدادات المقروءة.
- حزم Python وNode وRust وGo وRuby وPHP، وتعليمات التثبيت الصريحة التي تظهر في ملفات المهارة (pip، npm-family، apt/apk، cargo، go، gem، composer) دون تنفيذها.
- أسماء متغيرات البيئة ومفاتيح API الشائعة، بما في ذلك مفاتيح Cloud وService Account وDatabase URL؛ لا تُستخرج قيم الأسرار أو تُحفظ أو تُعاد أو تُعرض.
- أسماء مضيفي الخدمات الخارجية فقط، مع حذف مسارات URL ومعاملات الاستعلام وبيانات المستخدم من سجل المتطلبات. لا يجري اتصال بالشبكات.
- أنواع القدرات: تعليمات، سكريبتات محلية، ملفات تنفيذية، MCP، HTTP/OpenAPI، أدوات Dart أصلية داخل KELIVO، وتعريفات Workflow.

يشمل الفحص ملفات `SKILL.md` والملفات النصية/المرجعية والسكريبتات وملفات الإعداد وبيانات الاعتماديات وملفات `.env.example` والقوالب. تُفحص الملفات النصية التابعة بحد أقصى 256 KiB لكل ملف، ويظل `SKILL.md` حتى 2 MiB. تجاوز الحد لا يحذف الملف ولا يجعل الاستيراد جزئياً وحده؛ يسجل ملاحظة صريحة في تقرير المتطلبات حتى لا تُفسّر نتيجة الفحص المحدود على أنها جرد كامل.

### 2. تحقق قراءة فقط من البيئة الحالية

`SkillEnvironmentRequirementProbe` يقوم بالآتي فقط:

- ينتظر حالة تحميل EnvironmentProvider إن كانت متاحة بمهلة 8 ثوانٍ؛ كما أن فحص حالة Runtime له مهلة 8 ثوانٍ، حتى لا يعلّق عرض التقرير إذا تعذر تحميل البيئة.
- يتحقق من حالة Runtime وكونه PRoot معزولاً وجاهزاً.
- يستخدم `command -v` فقط مع أسماء أوامر من قائمة سماح محددة وبحد أقصى 64 أمراً، للتحقق من وجود الأمر في **PRoot الأساسي فقط**.
- يفحص وجود اسم متغير البيئة في قائمة إعدادات KELIVO، ولا يقرأ قيمة السر ولا يختبر صلاحيتها.
- يعرض مدير الحزم المتوقع حسب التوزيعة بوصفه استنتاجاً، لا تحققاً من التثبيت.

لا يثبت أي حزم، ولا يشغّل ملفات المهارة، ولا يشغّل خادم MCP، ولا ينفذ أوامر التثبيت المكتشفة، ولا يتصل بـ API أو خدمة خارجية. وجود أمر في PRoot الأساسي لا يثبت وجوده داخل Skill-owned Runtime Profile.

### 3. التمييز بين التوافق والجاهزية

يعرض التقرير حالات منفصلة بدلاً من ادعاء عام بأن المهارة جاهزة:

- أوامر موجودة في PRoot الأساسي / أوامر مفقودة / أوامر لم يمكن فحصها.
- حزم معلقة حتى إنشاء Skill Runtime Profile والتحقق من الحزم داخله.
- Manager مدعوم حالياً (apt/apk بحسب التوزيعة، pip/uv، npm family) أو ecosystem غير مدعوم حالياً في مدير حزم KELIVO (مثل Rust/Go/Ruby/PHP في هذا المسار الحالي).
- اسم متغير إعداد موجود في KELIVO أو مفقود؛ هذا لا يثبت أن API key صالح.
- خدمة خارجية مكتشفة لكنها لم تُختبر ولم يتم الاتصال بها.
- Script يتطلب Runtime Profile وموافقة التنفيذ، أو MCP/API/Workflow adapter، أو تطوير موائم Native داخل التطبيق.

يُذكر الدليل ومسار الملف الذي أظهر المتطلب كلما أمكن. كما تُعرض ملاحظات عندما يتعذر تحليل ملف بسبب ترميز غير نصي أو تجاوز حد الفحص.

### 4. العرض بعد التثبيت والفحص اللاحق

- بعد كل عملية تثبيت Skill من واجهة المكتبة، تظهر نافذة تقرير تشمل الاكتمال والملفات والقدرات وسجل المتطلبات المفصل بالعربية.
- استجابة `extension_install` في المحادثة تتضمن متطلبات البيئة لكل مهارة تم تثبيتها.
- `extension_inspect` يعيد فحصاً حديثاً للمتطلبات عند طلب المستخدم، بدلاً من الاعتماد على تقرير ثابت فقط.
- المهارات القديمة التي لا تحتوي سجل المتطلبات، أو التي لا تتطابق بصمة فهرس المتطلبات فيها مع بصمة ملفات المهارة، يعاد تحليل ملفاتها المحلية ويحدّث sidecar فقط. لا يعاد تثبيت المهارة ولا تعديل ملفاتها ولا تنفيذها.

### 5. Skill Composition واستخدام المهارة بعد تثبيتها

يرسل مخطط Skill Composition فهرس متطلبات كل مهارة مختارة ضمن `selectedSkillRequirements` وسياسة صريحة `discovery_before_execution`. تعليمات المساعد تلزمه بمراجعة التقرير قبل الاعتماد على القدرات التنفيذية، والتمييز بين المساعدة النصية الممكنة وبين تشغيل سكريبت/موصل غير مدعوم. يستطيع المستخدم الاستفسار عن المهارة مباشرة بعد تثبيتها؛ لا يتطلب ذلك تثبيت الاعتماديات أولاً، لكن لا تُدّعى قابلية تشغيل أداة غير موجودة.

## الاختبارات المضافة

- تحليل metadata وSKILL.md والسكريبتات وملفات MCP/OpenAPI و`.env.example`.
- اكتشاف Python/Node/Rust toolchains من ملفات الاعتماديات حتى عند عدم وجود ملفات سكريبت.
- تحليل أوامر تثبيت الحزم نصياً من دون تنفيذها، والتحقق من الحزم المعيّنة وأسمائها.
- اكتشاف أسماء `OPENAI_API_KEY` و`AWS_ACCESS_KEY_ID` و`DATABASE_URL` و`GOOGLE_APPLICATION_CREDENTIALS` من دون إعادة قيم الأمثلة.
- التحقق من اقتصار الخدمات الخارجية على أسماء المضيفين وعدم الاتصال بها.
- التوافق مع MCP/API/Workflow/Native capabilities ورسائل متطلبات الموائم.
- تحديث سجلات المهارات القديمة عند غياب الفهرس أو اختلاف بصمة المصدر.
- التحقق من أن تجاوز حد الفحص يسجل ملاحظة ولا يغيّر اكتمال استيراد الملفات.
- التحقق من التقرير العربي وسياسة المساعد وحقن متطلبات المهارات المختارة في Composition.

تم ربط الاختبارات المركزة في `.github/workflows/android-build.yml` عبر `phase13j_ci_self_test` و`phase13j_preflight` و`phase13j_tests` بعد اختبارات 13I. يحدد runner الاختبارات القديمة بالاسم عبر `--plain-name` حتى لا يعيد تشغيل بقية الاختبارات التاريخية داخل ملفات الاختبار المشتركة. لم تُعد اختبارات 13A–13D.

## نتائج الفحص في بيئة العمل الحالية

نجحت محلياً:

- Phase 13J Static Preflight (21 فحصاً بنيوياً بعد إضافة متطلبات الاكتشاف).
- Phase 13J CI Self-Test.
- Bash syntax checks لسكربتات المرحلة.
- تحليل YAML لملف GitHub Actions.

لم تتوفر Flutter وDart وGradle في بيئة العمل الحالية؛ لذلك لم تُنفذ اختبارات Flutter الفعلية أو Dart Analysis أو بناء APK ARM64. يلزم تشغيل GitHub Actions ثم تجربة تثبيت Skill حقيقي، وفحص تقريره، وسؤال المساعد عنه، والتأكد من أنه يفرق بين التعليمات المتاحة والقدرات التي تتطلب تطوير البيئة.

## الحدود المعروفة

هذا إصدار اكتشاف متطلبات، وليس مثبت حزم عاماً ولا منشئ Runtime Profiles ولا مُشغّل MCP أو Workflow. تحليل ملفات المهارة ثابت ومحدود بأنواع الملفات والأدلة المذكورة؛ لا يمكنه استنتاج كل اعتماد مخفي أو خدمة غير موثقة أو متطلب يظهر فقط أثناء التنفيذ. لذلك يعلن الملاحظات وحدود الفحص ولا يعتبر عدم اكتشاف المتطلب إثباتاً لعدم وجوده. تطوير موائمات ومديري حزم وملفات التشغيل المعزولة يأتي في مراحل لاحقة بعد موافقة المستخدم وعلى أساس التقرير.

**الحفاظ على الاستقلال:** لم تتغير ملكية المهارات الأصلية ولا علاقاتها بـ Skill Packs. لم تتم إضافة أدوات خارجية أو حزم للنظام أثناء هذه المرحلة، ولم تتغير سياسة موافقة تشغيل المهارات.
