# Phase 13E — إصلاح نطاق Runtime Profile في محادثات PRoot الخاصة

## ملخص نتيجة اختبار الهاتف

أكدت لقطات الهاتف ثلاث نقاط:

1. اختبار اتصال API الأساسي نجح وأعاد النموذج `OK`.
2. ظهر استدعاء `environment_status`، لكن بطاقة نتيجة الأداة كانت مطوية، كما أن الرد النصي التالي لم يعرض حالة Ubuntu/PRoot المطلوبة؛ لذلك لا تكفي الصور لإثبات صحة محتوى تقرير البيئة.
3. وصل أمر Shell إلى حد التنفيذ بعد طلب الموافقة، لكنه أعاد `runtime_profile_not_found` بدل تشغيل الأمر داخل Ubuntu.

هذا يجعل الخطأ الحالي مختلفًا عن انقطاع API السابق وعن فشل تسجيل PRoot. رسالة `runtime_profile_not_found` تصدر من حلّ ملف Runtime Profile، قبل بدء الأمر.

## السبب في المصدر

كان `WorkspaceToolsService` يضيف مخطط `runtime_profile_id` وأداة `runtime_profile` إلى جميع سياقات Workspace، بما فيها المساحات المؤقتة الخاصة بالمحادثة.

لكن `resolveConversationScoped` ينشئ مساحة محادثة مؤقتة لا ترتبط بمشروع محفوظ، وتعمل مباشرة على بيئة Android PRoot الأساسية. لا تملك هذه المساحة ملف Runtime Profile خاصًا بمشروع. ومع ذلك، كان معالج Shell يحاول حل أي `runtime_profile_id` يرسله النموذج، أو أي قيمة افتراضية قديمة موجودة في سياق تالف/منقول. عند عدم وجود السجل في `RuntimeProfileService` كان التنفيذ يتوقف بـ`runtime_profile_not_found`.

## التغييرات

- جعل مخطط Shell يحذف `runtime_profile_id` من محادثات `conversationScoped`.
- إخفاء أداة إدارة `runtime_profile` في هذا السياق؛ فهي مخصصة للمشاريع/المهارات التي تملك سياقًا محفوظًا.
- إضافة تعليمات صريحة إلى Prompt بأن مساحة المحادثة تستخدم PRoot الأساسي، وألا ينشئ النموذج أو يمرر معرّف Runtime Profile.
- إضافة حماية في الخلفية: لا تستدعي محادثة خاصة `RuntimeProfileService.resolveExecution` مطلقًا، حتى عند وصول حقل قديم/مخترع أو قيمة افتراضية قديمة. يُسجل التجاوز في نتيجة Shell عبر `runtime_profile_ignored` و`runtime_profile_note` حتى لا يكون صامتًا.
- الإبقاء على طلب الموافقة اليدوية الجديدة لكل أمر Shell في المحادثات الخاصة، بما في ذلك Full Access. لا يبدأ PRoot قبل الموافقة.
- عدم تغيير سلوك مساحة Workspace المشروع: لا تزال ملفات Runtime Profiles الصالحة تُحل وتطبق كما كانت، ويظل المعرّف الصريح غير الموجود خطأً في سياق المشروع.

## اختبارات الانحدار

تم توسيع الاختبار الموجود في مجموعة Phase 13E النشطة `environment_status_tool_test.dart` ليحاكي:

- مساحة محادثة خاصة مع `defaultRuntimeProfileId` قديم.
- قيمة `runtime_profile_id` غير موجودة مررها النموذج.
- غياب أداة `runtime_profile` وحقل `runtime_profile_id` من تعريفات أدوات المحادثة.
- أن طلب موافقة Shell اليدوية يظهر أولًا، ولا يستقبل Runtime الأمر قبل الموافقة.
- بعد الموافقة، يصل الأمر إلى PRoot الأساسي وينجح، وتوضح النتيجة أن معرّف الملف الشخصي تم تجاهله.

كما توسع فحص Phase 13E Preflight لحراسة هذه السياسة. ما زالت اختبارات 13A و13B و13C و13D مستبعدة من Workflow النشط.

## حدود التحقق

اجتاز فحص CI الذاتي وصياغة سكريبتات Shell محليًا. لم تتوفر Flutter/Dart في بيئة التجهيز؛ لذلك لم تُشغّل اختبارات Flutter الفعلية أو Dart Analyzer أو بناء APK هنا. يجب أن يثبت GitHub Actions نجاح اختبار `environment_status_tool_test.dart` وبناء ARM64، ثم يثبت الهاتف أن `printf KELIVO_TOOL_OK` يعمل بعد موافقة جديدة.

## ملاحظة منفصلة عن environment_status

تُظهر الصور استدعاء الأداة، لكنها لا تعرض محتوى نتيجة الأداة. كما أن الرد النصي الظاهر بعدها يتحدث عن تثبيت Skill وليس عن حالة Ubuntu/PRoot. لا يمكن تحديد ما إذا كان ذلك ردًا غير مطابق من النموذج أو محتوى أداة غير صحيح دون فتح بطاقة Tool Result وقراءة JSON الفعلي. ينبغي حفظ ذلك كتحقق منفصل بعد إصلاح Shell.
