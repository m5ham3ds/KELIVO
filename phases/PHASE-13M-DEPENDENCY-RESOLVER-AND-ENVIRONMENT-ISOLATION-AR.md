# PHASE13M — Dependency Resolver & Isolated Environments

## الهدف

تجعل هذه المرحلة تجهيز اعتماديات المهارات قابلاً للتكرار والاسترجاع، مع إبقاء كل Runtime Profile مستقلاً عن الملفات والاعتماديات الخاصة بالملفات الأخرى. لا تعتمد المرحلة على أسماء المهارات الست المستخدمة في اختبارات المحتوى؛ فالمنظومة تستقبل أي Skill متوافق مع عقد الاستيراد العام، وتحدد التوافق من نوع القدرة والمفسّر ومدير الحزم والموائم المتاح، لا من اسم المهارة أو مجالها.

## ما نُفّذ في المصدر

### 1. لقطات الاعتماديات لكل Runtime Profile

أضيف سجل `RuntimeProfileSnapshotRecord` وخدمات إنشاء اللقطة واستعادتها وحذفها وعرضها.

تغطي اللقطة:
- جذر Python المملوك للـ Profile.
- جذر Node.js المملوك للـ Profile.
- ملفات القفل الخاصة ببيئة Profile متى وجدت.
- بصمة SHA-256 وحجم الأرشيف وهوية المالك والنطاق والأنظمة البيئية وتاريخ الإنشاء.

تُحفظ اللقطات خارج جذر Profile حتى لا تدخل في الأرشيف نفسه. وقبل الاستعادة، يتحقق المحرك من بصمة الملف وحجمه ومسارات الأعضاء والأنظمة البيئية ومجلد الأرشيف المسموح به. ثم يستخرج إلى مجلد مرحلي ويستبدل فقط جذور الاعتماديات التي تملكها تلك اللقطة.

حدود التخزين: 10 لقطات لكل Profile، و512 MiB للّقطة الواحدة، و2 GiB إجمالاً للـ Profile. عمليات مدير الحزم تحتفظ بأحدث 10 نقاط استرجاع تلقائياً بحذف الأقدم عند الحاجة؛ أما اللقطات اليدوية فلا تحذف لقطات موجودة تلقائياً.

### 2. قفل الصيانة والتزامن

تستخدم عمليات Snapshot/Restore/Delete قفل Runtime Profile نفسه الذي تستخدمه عملية تشغيل المهارة. لا يمكن تغيير الاعتماديات أو استعادة لقطة بينما توجد عملية نشطة في Profile. كما أن عمليات إدارة الحزم المرتبطة بـ `profile_id` تحجز Profile، وتنشئ لقطة قبل أول تغيير، ثم تحاول استعادتها عند فشل العملية. إذا فشلت الاستعادة، يبقى مسار rollback التقليدي للحزم كخطة احتياطية ويُسجل الفشل في سجل العملية. عملية الاستعادة نفسها تنفذ التبديل عبر staging ونسخة احتياطية مؤقتة، وتعيد الحالة السابقة إذا فشل تبديل أحد الجذور.

### 3. النطاق المشترك مقابل النطاق المعزول

**مهم:** لا تدّعي KELIVO عزل `apt/apk` لكل مهارة؛ فهما يغيران RootFS المشترك داخل PRoot. لذلك:
- تُعزل حزم Python وNode عند استخدامها عبر `profile_id` في جذور مملوكة للـ Profile.
- تُحفظ ملفات Lock الخاصة بنطاق Profile ضمن الجذر الملائم.
- تبقى عمليات `apt/apk` على مستوى RootFS المشترك، وتُستثنى من لقطات Profile.
- يعرض وصف أداة Runtime Profile هذا الفرق بدلاً من وصف كل الاعتماديات بأنها معزولة.

### 4. محلل التعارضات

أضيف `DependencyResolver` مستقل عن أسماء المهارات. يستقبل مطالبات اعتماديات تحمل اسم الحزمة والنظام البيئي ومفتاح جذر التثبيت والمالك ومدير الحزم وقيد الإصدار ومصدره.

- لا يعتبر اختلاف إصدارات الحزمة بين Profileين منفصلين تعارضاً.
- يكشف اختلاف الإصدارات الدقيقة داخل الجذر نفسه.
- يكشف اختيار مديري حزم مختلفين للجذر نفسه.
- لا يخمّن توافق قيود الإصدارات النطاقية؛ يعلّمها بأنها تحتاج إلى محلّل مدير الحزم الأصلي.
- يحتفظ بمصدر كل مطالبة (الملف والسطر) عندما يكون متاحاً.

المحلل لا يثبت أي حزمة ولا ينفذ سكريبتات install hooks.

### 5. سجل موائمات مديري الحزم

أضيف `PackageManagerAdapterRegistry` لتسجيل موائمات مديري الحزم بشكل مستقل عن خدمة العمليات. موائمات apt/apk/pip/uv/npm/pnpm/yarn/bun الحالية سُجلت كموائمات افتراضية. يمكن إضافة موائم جديد من كود التطبيق دون إعادة كتابة محرك التنفيذ. لا يستطيع ZIP مهارة تسجيل كود Dart أو استبدال موائم موثوق وقت التشغيل.

### 6. أداة Runtime Profile

أضيفت الإجراءات:
- `snapshot`
- `snapshots`
- `restore_snapshot`
- `delete_snapshot`

تتطلب العمليات المغيّرة موافقة المستخدم. كل سجل لقطة مربوط بالـ Profile والمالك، ولا تُعرض لمالك آخر.

## مبدأ دعم المهارات العامة — شرط معماري دائم

المهارات الست المرفقة محتوى اختباري فقط وليست قائمة مدعومة مغلقة. يجب أن يبقى KELIVO متوافقاً مع بنية Agent Skills العامة وملفات `SKILL.md` والموارد المصاحبة، ويجب ألا يحتوي التنفيذ على فروع بأسماء تلك المهارات.

التمييز المطلوب في KELIVO هو بين:
1. **Imported**: تم استيراد المهارة وملفاتها بأمان.
2. **Discovered**: تم اكتشاف تعليماتها ومتطلباتها وقدراتها المعلنة.
3. **Compatible**: يوجد عقد وقدرة وموائم مناسب لهذا النوع.
4. **Environment Ready**: البيئة المطلوبة والحزم والإعدادات تحققت داخل Runtime Profile الصحيح.
5. **Execution Proven**: شُغلت القدرة بإذن مستقل، وتم التحقق من نتيجة التنفيذ ومخرجاتها.

استيراد مهارة من Claude/Codex أو مستودع Agent Skills لا يعني أن كل أداة خارجية معلنة بها أصبحت متاحة تلقائياً. كل نوع يحتاج إلى موائم تطبيق موثوق ومراجَع. لا يسمح باستيراد ZIP أن يضيف شيفرة Dart أو يسجل موائماً تنفيذياً بنفسه.

### التغطية التنفيذية التي يجب عرضها بدقة

| النوع | ما يمكن فعله في المصدر الحالي | ما لا يجوز ادعاؤه |
|---|---|---|
| `SKILL.md` والتعليمات | القراءة والإرشاد والتأليف بمساعدة المساعد | لا يثبت تشغيل سكريبت أو خدمة |
| Local Script | تشغيل نقاط الدخول المحددة والمدعومة حالياً: Python وBash وNode، عبر `SkillExecutor` وبروفايل وموافقة | لا يعني دعم كل لغات السكريبت حتى الآن |
| CLI Binary | اكتشاف الأمر وفحص توفره في البيئة | لا يعني وجود منفذ مستقل لكل CLI أو أن فحص Base PRoot يكفي |
| MCP Server | اكتشاف التعريفات والمتطلبات | لا يعني تشغيل خادم MCP من ZIP المهارة |
| HTTP/OpenAPI | حفظ/اكتشاف وصف التكامل والمتطلبات | لا يعني وجود اتصال API أو ربط آمن للاعتمادات |
| Workflow | حفظ التعريف وتحليله | لا يعني وجود مشغّل Workflow متوافق لكل صيغة |
| Native KELIVO Tool | يتطلب إضافة موائم داخل التطبيق | لا يمكن للمهارة حقن شيفرة Dart في التطبيق |

هذه القيود هي جرد التغطية الحالية وليست قيداً على أنواع المهارات التي يمكن استيرادها. توسيع موائمات التنفيذ يجب أن يكون عاماً ويستند إلى العقد ونوع القدرة، لا إلى أسماء أو ملفات حزمة بعينها.

## الاختبارات المضافة أو المستهدفة في CI

- دورة Snapshot/Restore/Delete باستخدام Runtime fake حقيقي على نظام المضيف حيث يتاح، ورفض استعادة أرشيف تالف قبل المساس بالحالة الحالية.
- التحقق من مسارات الأرشيف الآمنة وحجم اللقطة.
- عرض إجراءات Snapshot في أداة Runtime Profile.
- تسجيل موائمات مديري الحزم ومنع التسجيل المكرر.
- كشف تعارض النسخ داخل الجذر نفسه وعدم كشف اختلاف النسخ بين Profiles مستقلة.
- الحفاظ على اختبارات Phase 13L المركزة وعدم إعادة 13A–13D.

## الحدود التي لم تكتمل في هذه المرحلة

- `apt/apk` لا يزالان يعدلان RootFS مشتركاً؛ لم يتحول PRoot إلى نظام RootFS مستقل لكل مهارة.
- لا توجد بعد حاويات/Namespaces أو حدود نواة Linux قوية؛ PRoot ليس Sandbox أمنيّاً صلباً.
- محلل التعارضات لا يفسر SemVer/ranges بنفسه؛ يحتاج إلى مدير الحزم الأصلي.
- موائمات MCP وHTTP API وWorkflow وNative Tools لم تُنفذ كلها في هذه المرحلة.
- لا تُضاف مفسرات جديدة تلقائياً لمجرد أن محلل المتطلبات اكتشف ملفاً بامتداد جديد.
- اختبارات Flutter وAndroid وAPK يجب إثباتها في GitHub Actions/الجهاز؛ فحص المصدر المحلي لا يكفي.

## شروط قبول PHASE13M

1. يمكن حفظ لقطة واعتمادها واستعادتها دون إدخال ملفات من Profile آخر.
2. لا تعمل الاستعادة إذا كانت البصمة أو الحجم أو المسار أو ملكية Profile غير صحيحة.
3. لا يتم تغيير Profile نشط أثناء التشغيل.
4. أي فشل بعد بدء تثبيت اعتماديات Profile يحاول الرجوع إلى اللقطة السابقة ويسجل النتيجة.
5. تبقى حزم النظام المشتركة معلنة بوضوح خارج نطاق العزل.
6. لا تظهر أي إحالات ثابتة إلى أسماء المهارات الست في محرك الاعتماديات أو التسجيل.
7. تبقى أنواع المهارات غير المدعومة قابلة للاستيراد والإرشاد مع إظهار الموائم المفقود، لا إسقاطها أو الادعاء بتشغيلها.
