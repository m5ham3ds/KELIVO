## 1. الملخص التنفيذي

أبلغ المستخدم عن فشل تثبيت APK جديد فوق نسخة Kelivo المثبتة، مع اضطراره إلى حذف النسخة القديمة أولاً. تم التحقق من أن هذه ليست مشكلة شكلية في واجهة التنزيل أو مدير الملفات، بل يوجد خلل حقيقي في سلسلة توقيع APK داخل CI.

**السبب الأساسي المؤكد:** بناء Release يعود إلى توقيع Debug عند غياب `android/key.properties`. وبما أن GitHub Actions يستخدم runners مؤقتة، فإن مفتاح Debug الافتراضي يُنشأ من جديد في بيئات البناء المختلفة. لذلك لا تحمل ملفات APK المتعاقبة شهادة توقيع واحدة.

تم استخراج شهادة التوقيع من APK الخاص بالتشغيلين #211 و#217 ومقارنة بصمة SHA-256 للشهادة نفسها. النتيجة: بصمتان مختلفتان. وهذا يكفي لجعل Android يرفض تثبيت APK #217 كتحديث فوق APK #211، رغم تطابق Application ID.

**القرار:** تعتبر هذه المشكلة مانع إصدار (Release Blocker). لا يجوز اعتبار بناء APK ناجحاً دليلاً على أن APK قابل للتحديث فوق النسخة المثبتة. ولا تُغلق هذه المشكلة إلا بعد نجاح اختبار ترقية حقيقي دون حذف التطبيق.

## 3. السبب الجذري في المشروع

### 3.1 مسار توقيع Release الحالي

في `android/app/build.gradle.kts` يقرأ المشروع الملف:

```kotlin
val keystorePropertiesFile = rootProject.file("key.properties")
```

ثم يختار إعداد التوقيع:

```kotlin
signingConfig = if (keystorePropertiesFile.exists()) {
    signingConfigs.getByName("release")
} else {
    signingConfigs.getByName("debug")
}
```

بالتالي، إذا لم يكن `android/key.properties` موجوداً داخل بيئة البناء، يتحول توقيع Release إلى مفتاح Debug الافتراضي.

الملف `android/key.properties` مستثنى من Git عبر `.gitignore`، وهذا صحيح من ناحية حماية الأسرار؛ لكن لا توجد في Workflow الحالي خطوة تهيئ ملف التوقيع من بيانات سرية ثابتة قبل بناء APK. كما لم يظهر في إعدادات Workflow مسار يحقن Keystore ثابتاً في عملية البناء.

### 3.2 لماذا تتغير الشهادة في كل تشغيل؟

GitHub-hosted runner بيئة بناء مؤقتة. عند استخدام Debug signing دون إحضار مفتاح ثابت، يمكن إنشاء Debug keystore جديد داخل بيئة ذلك التشغيل.

الدليل العملي من الملفات الموقعة:

- شهادة #211 صالحة ابتداءً من 20:59:54 UTC.
- شهادة #217 صالحة ابتداءً من 22:15:58 UTC.
- بصمتا الشهادتين مختلفتان.

إذن نجاح `assembleRelease` وفحص ABI وحساب SHA-256 لا يثبت ثبات هوية توقيع التطبيق.

### 3.3 مشكلة رقم الإصدار

وجدت أيضاً أن:

- `pubspec.yaml` في commit #211 يحتوي `version: 1.3.4+84`.
- `pubspec.yaml` في رأس `main` الحالي ما زال يحتوي `version: 1.3.4+84`.
- `android/app/build.gradle.kts` يربط `versionCode` بـ`flutter.versionCode` و`versionName` بـ`flutter.versionName`.

وبالتالي فإن #211 و#217 أُنتجا من رقم البناء نفسه: `versionCode = 84`.

تسمح وثائق Android بتثبيت تحديث يحمل versionCode مساوياً أو أعلى من الموجود في بعض مسارات التثبيت؛ لذلك لا أُصنّف تساوي الرقم وحده باعتباره سبب رفض #211 ← #217. لكنه خلل مستقل في إدارة الإصدارات: يجب أن يرتفع رقم البناء مع كل إصدار تحديث رسمي. كما تشترط Google Play أن يكون versionCode للتحديث أعلى من الإصدار الحالي.

- [Android Developers — Sign your app](https://developer.android.com/studio/publish/app-signing)
- [Android Developers — Version your app](https://developer.android.com/studio/publish/versioning)

## 4. الأثر على المستخدم

الخلل يمنع سلوك التحديث الطبيعي للتطبيق، ويجبر المستخدم على إزالة النسخة القديمة قبل تثبيت الجديدة عندما لا تتطابق شهادتا التوقيع.

إزالة التطبيق ليست حلاً مقبولاً كإجراء تحديث اعتيادي؛ إذ قد تؤدي إلى فقد بيانات التطبيق المحلية، بما في ذلك المحادثات والإعدادات والبيانات المخزنة، بحسب مكان تخزينها وسياسة النسخ الاحتياطي.

الأثر لا يقتصر على #211 و#217. ما دام Release fallback يستخدم Debug signing داخل بيئات مؤقتة، فإن احتمال اختلاف الشهادة يتكرر في تشغيلات CI المستقبلية.

## 5. خطة الإصلاح الإلزامية

هذه الخطة التزام هندسي مطلوب، وليست ادعاءً بأن الإصلاح نُفّذ بالفعل.

### 5.1 توقيع ثابت ودائم

1. اعتماد Keystore واحد ثابت لهوية تطبيق `com.psyche.kelivo`، وعدم توليد مفتاح جديد لكل عملية بناء.
2. حفظ ملف Keystore وكلمات المرور في GitHub Actions Secrets أو بيئة أسرار محمية مناسبة.
3. إنشاء `android/key.properties` مؤقتاً أثناء Workflow من الأسرار، وعدم رفعه إلى Git أو تضمين محتواه في السجلات أو الـArtifacts.
4. إيقاف Debug signing fallback في أي Workflow ينتج APK قابلاً للتوزيع على أنه تحديث Release.
5. إذا غابت بيانات التوقيع الثابتة، يجب أن يفشل بناء Release بوضوح قبل رفع APK؛ لا يُسمح بإنتاج APK جديد يحمل شهادة مؤقتة.
6. تثبيت بصمة شهادة التوقيع العامة المتوقعة في إعداد التحقق، وفحص كل APK قبل رفعه.
7. الاحتفاظ بنسخة احتياطية آمنة من Keystore خارج GitHub أيضاً؛ فقدان المفتاح الدائم يهدد القدرة على إصدار تحديثات متوافقة مستقبلاً.

**تنبيه انتقال مهم:** ملفات APK لا تحتوي المفتاح الخاص الذي أنشأ التوقيع. إذا كان لدى المستخدم إصدار مثبت بشهادة Debug مؤقتة لم يعد مفتاحها الخاص متاحاً، فلن يكفي إنشاء Keystore دائم جديد لجعل هذا الإصدار القديم يقبل التحديث. يجب أولاً البحث عن المفتاح الأصلي في نسخ احتياطية أو أسرار محفوظة. إذا لم يُعثر عليه ولم تتوفر سلسلة تدوير صالحة، فقد تتطلب عملية الانتقال الأولى إعادة تثبيت واحدة. بعد اعتماد المفتاح الثابت، يجب ألا يتكرر هذا الانقطاع في التحديثات اللاحقة.

### 5.2 إدارة versionCode

1. جعل versionCode متزايداً بصورة رتيبة لكل إصدار APK يُقصد به تحديث إصدار سابق.
2. اختيار مصدر رقم بناء ثابت وموثوق في CI، مثل رقم تشغيل Workflow المتزايد، أو عملية إصدار موثقة ترفع رقم البناء في المصدر.
3. الحفاظ على versionName منفصلاً عن versionCode؛ يمكن أن يبقى اسم الإصدار `1.3.4` بينما يرتفع رقم البناء.
4. رفض رفع Artifact إذا كان رقم البناء لا يحقق قاعدة الإصدار المعتمدة.

### 5.3 اختبار التحديث الحقيقي في CI

يجب إضافة بوابة مستقلة لا تكتفي بفحص نجاح البناء:

1. تثبيت APK سابق موقّع بالمفتاح الدائم على Android Emulator.
2. الاحتفاظ ببيانات التطبيق التجريبية بعد التثبيت، مثل قيمة إعداد أو سجل محادثة اختباري.
3. بناء APK جديد من commit لاحق، مع نفس Application ID ونفس شهادة التوقيع ورقم بناء أحدث.
4. تنفيذ `adb install -r new.apk` فوق التطبيق المثبت، دون حذف التطبيق أو استخدام `adb uninstall`.
5. اشتراط نجاح التثبيت دون رسالة `INSTALL_FAILED_UPDATE_INCOMPATIBLE` أو أي خطأ توقيع/تخفيض إصدار.
6. فتح التطبيق بعد التحديث والتحقق من بقاء بيانات الاختبار.
7. فحص شهادة APK الجديد ومقارنتها ببصمة الشهادة الثابتة المتوقعة.
8. رفع APK وملف SHA-256 وبيانات التوقيع العامة ورقم البناء بعد اجتياز هذه البوابة فقط.

## 7. سياسة التعامل مع المشكلة

- هذه المشكلة **Release Blocker** وليست تحسيناً اختيارياً.
- لا يجوز إعلان APK جديد على أنه تحديث جاهز ما لم يثبت تطابق شهادة التوقيع مع الإصدار السابق المعتمد.
- لا يجوز اعتبار نجاح Flutter Analyze أو Robolectric أو بناء APK بديلاً عن اختبار الترقية فوق نسخة مثبتة.
- لا يُسمح بحذف بيانات المستخدم أو طلب إزالة التطبيق باعتباره حلاً دورياً لكل إصدار.
- يجب تنفيذ الإصلاح على `main) وفق سياسة الفروع المعتمدة، أو على فرع العمل الوحيد المسموح به إن استُخدم.
- يجب تحديث هذا التقرير إلى **مُصلح ومقبول** فقط بعد اجتياز جميع معايير القبول وإرفاق روابط تشغيل CI الداعمة.

## 8. حالة التنفيذ عند إنشاء التقرير

تم تأكيد اختلاف التوقيع من APK #211 و#217، ومراجعة مسار Gradle الذي أدى إليه، وتحديد ثبات versionCode عند 84.

**ما تم إنجازه:** التشخيص، استخراج بصمات شهادات التوقيع، تحديد السبب الجذري، وتوثيق خطة الإصلاح ومعايير القبول.

**ما لم يتم إنجازه:** لم يُغيّر إعداد التوقيع، ولم يُنشأ Keystore جديد، ولم تُعدّل أرقام الإصدارات، ولم يُنفّذ اختبار تحديث على Emulator أو هاتف فعلي. لا تعتبر المشكلة مغلقة بمجرد إضافة هذا التقرير.

**الالتزام:** تبقى هذه المشكلة مسجلة كمانع إصدار. يجب معالجة ثبات التوقيع ورقم البناء وإثبات التحديث دون إزالة التطبيق قبل اعتماد مسار توزيع APK كتحديث اعتيادي.
